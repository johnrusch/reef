# Phase 8: Change Visualization - Research

**Researched:** 2026-02-28
**Domain:** React UI components — SVG DOM manipulation, PlantUML element highlighting, Radix UI tooltips, Tailwind CSS badge styling
**Confidence:** HIGH

## Summary

Phase 8 is a pure frontend rendering phase. The backend pipeline (ChangeTrackingService → SQLite → IPC → diagramStateStore) was completed in Phase 7 and is fully verified. Phase 8 consumes the `affectedElements: AffectedElement[]` data already available in `useDiagramStateStore` and makes it visible inside the diagram.

There are two distinct UI problems to solve. First, changed C4 elements need amber/orange visual styling distinguishable from normal elements — this must be applied post-render because the SVG is generated by PlantUML and injected via `dangerouslySetInnerHTML`. The approach is DOM manipulation after the SVG is rendered: traverse the SVG, find `<g id="elem_{elementId}">` groups matching changed element IDs, and apply CSS class or inline style. This is the same pattern already used for clickable elements. Second, a change badge (count with tooltip listing affected files) must be overlaid on the diagram panel. This is a React overlay positioned absolutely within `DiagramPanel`, not inside the SVG.

The key design insight is that two separate approaches are needed: (1) SVG DOM post-processing for element coloring and (2) React overlay components for badges and tooltips. The project does not have `@radix-ui/react-tooltip` installed — only `@radix-ui/react-dialog`, `@radix-ui/react-dropdown-menu`, and `@radix-ui/react-tabs` are present. Tooltip behavior will be implemented using CSS hover states and HTML `title` attributes for simple cases, or a lightweight custom tooltip using Tailwind for the file-list tooltip in VISU-03. No new npm packages are required.

**Primary recommendation:** Post-process the rendered SVG via a `useEffect` that runs after `dangerouslySetInnerHTML` injection. Add a `ChangeBadge` overlay component to `DiagramPanel` that reads from `diagramStateStore`. Wire these components using the existing `affectedElements` Map already populated by Phase 7.

### Pattern 1: SVG DOM Post-Processing for Element Highlighting (VISU-01, VISU-04)

**What:** After `svgContent` is injected via `dangerouslySetInnerHTML`, a `useEffect` runs to find SVG `<g>` elements with `id="elem_{elementId}"` and applies styling.

**When to use:** Runs whenever `svgContent` or `highlightedElementIds` prop changes in `PlantUMLRenderer`.

**How PlantUML SVG elements are structured:**
PlantUML C4 diagrams generate SVG elements with the pattern `<g id="elem_{sanitizedId}">`. The existing click handler in `PlantUMLRenderer` already traverses this structure (`id.startsWith('elem_')` → `id.replace('elem_', '')`). Phase 8 uses the same pattern in reverse: given a list of `elementId` strings, find `elem_{elementId}` groups in the DOM.

**Example:**
```typescript
// In PlantUMLRenderer.tsx — new prop and useEffect

interface PlantUMLRendererProps {
  // ... existing props ...
  /** Element IDs to highlight as directly changed (amber fill) */
  directChangedIds?: string[];
  /** Element IDs to highlight as inherited changes (amber border only) */
  inheritedChangedIds?: string[];
}

// After SVG is rendered and injected:
useEffect(() => {
  if (!svgContent || !containerRef.current) return;

  // Reset all previously highlighted elements
  const allHighlighted = containerRef.current.querySelectorAll('[data-changed]');
  allHighlighted.forEach(el => {
    el.removeAttribute('data-changed');
    (el as SVGElement).style.filter = '';
    (el as SVGElement).style.outline = '';
  });

  // Apply direct change highlighting (amber fill via filter/style)
  for (const elementId of (directChangedIds || [])) {
    const group = containerRef.current.querySelector(`[id="elem_${elementId}"]`);
    if (group) {
      group.setAttribute('data-changed', 'direct');
      // Apply amber tint via CSS filter (doesn't require modifying SVG fill colors)
      // Or inject a rect overlay with amber stroke
    }
  }

  // Apply inherited change highlighting (amber border only)
  for (const elementId of (inheritedChangedIds || [])) {
    const group = containerRef.current.querySelector(`[id="elem_${elementId}"]`);
    if (group) {
      group.setAttribute('data-changed', 'inherited');
    }
  }
}, [svgContent, directChangedIds, inheritedChangedIds]);
```

**SVG styling approach:** The safest cross-browser approach for amber overlay is to inject a `<style>` block into the SVG after render:
```typescript
// Inject scoped style into SVG to highlight changed elements
const styleEl = document.createElement('style');
styleEl.textContent = `
  [data-changed="direct"] rect, [data-changed="direct"] polygon {
    fill: rgba(251, 191, 36, 0.25) !important;  /* amber-400/25 */
    stroke: rgb(245, 158, 11) !important;        /* amber-500 */
    stroke-width: 2 !important;
  }
  [data-changed="inherited"] rect, [data-changed="inherited"] polygon {
    stroke: rgb(245, 158, 11) !important;        /* amber-500 */
    stroke-width: 2 !important;
    stroke-dasharray: 4 2 !important;
  }
`;
const svgEl = containerRef.current.querySelector('svg');
if (svgEl && !svgEl.querySelector('style[data-reef-changes]')) {
  styleEl.setAttribute('data-reef-changes', '');
  svgEl.prepend(styleEl);
}
```

**Why CSS `!important` is needed:** PlantUML SVG has inline `fill` and `stroke` attributes on shapes. `!important` in a `<style>` block overrides inline attributes.

**Warning:** The SVG is re-generated (and DOM is wiped and replaced) every time `content` prop changes — i.e., when the user switches diagrams or regenerates. The `useEffect` must run after each `svgContent` change to reapply highlights.

### Pattern 2: ChangeBadge Component (VISU-02, VISU-03)

**What:** A React component overlaid on `DiagramPanel` (not inside SVG). Shows count of changed elements with a hover tooltip listing affected file paths.

**When to use:** Render when diagram state is `stale` AND `changedElementCount > 0`.

**Example:**
```typescript
// src/renderer/components/DiagramViewer/ChangeBadge.tsx
import React from 'react';

interface ChangeBadgeProps {
  directCount: number;
  inheritedCount: number;
  changedFiles: string[];
}

export const ChangeBadge: React.FC<ChangeBadgeProps> = ({
  directCount,
  inheritedCount,
  changedFiles,
}) => {
  const totalCount = directCount + inheritedCount;
  if (totalCount === 0) return null;

  return (
    // Position this as absolute inside DiagramPanel's relative container
    // Alongside the DiagramStateBadge (top-left, perhaps slightly offset)
    <div className="group relative">
      <div className="flex items-center gap-1.5 px-2.5 py-1.5 bg-amber-500/20 border border-amber-500/30 rounded-md cursor-help">
        <span className="text-xs font-medium text-amber-300">
          {directCount > 0 && (
            <span title="Directly changed elements">{directCount} changed</span>
          )}
          {directCount > 0 && inheritedCount > 0 && (
            <span className="text-amber-500/70 mx-1">·</span>
          )}
          {inheritedCount > 0 && (
            <span className="text-amber-400/70" title="Elements with changed children">
              {inheritedCount} affected
            </span>
          )}
        </span>
      </div>

      {/* Tooltip: visible on hover, lists affected files */}
      {changedFiles.length > 0 && (
        <div className="invisible group-hover:visible absolute top-full left-0 mt-1 z-50
                        min-w-64 max-w-sm bg-gray-900 border border-gray-700 rounded-lg
                        shadow-xl p-3">
          <p className="text-xs text-gray-400 font-medium mb-2">
            {changedFiles.length} file{changedFiles.length !== 1 ? 's' : ''} changed:
          </p>
          <ul className="space-y-0.5 max-h-48 overflow-y-auto">
            {changedFiles.map((file, i) => (
              <li key={i} className="text-xs text-gray-300 font-mono truncate" title={file}>
                {file.split('/').pop()}
              </li>
            ))}
          </ul>
        </div>
      )}
    </div>
  );
};
```

### Anti-Patterns to Avoid

- **Modifying PlantUML source with string regex:** The existing `DiagramPanel.tsx` stub (`highlightChangesInDiagram`) tries to inject `#FFE4B5` via regex on the PlantUML text before rendering. This approach is unreliable because (a) C4-PlantUML uses `Component()` / `Container()` macros, not raw `class`/`participant` keywords; (b) the regex pattern `/(class|component|participant)\\s+(${componentName})/` will never match C4 syntax like `Component(Services, "Services", "TypeScript", "...")`. This stub should be removed in Phase 8.

- **Using SVG filter on the entire `<g>` group:** CSS `filter: drop-shadow()` or `filter: brightness()` on a `<g>` element applies to all child elements uniformly. This can make text unreadable if the filter is too strong. Use targeted `fill`/`stroke` on descendant `rect`/`polygon` shapes instead.

- **Re-generating the diagram for highlighting:** Never trigger PlantUML re-generation just to show change highlights. Change highlighting is purely a post-render DOM decoration. The diagram content remains unchanged.

- **Using `innerHTML` to re-inject modified SVG:** After `dangerouslySetInnerHTML` sets the SVG, do not re-assign `innerHTML` to apply changes — this destroys and rebuilds all DOM nodes, losing event listeners. Use `querySelector` + `setAttribute`/`style` on existing DOM nodes.

- **Tooltip using `title` attribute for file list:** Native `title` tooltips are browser-controlled and cannot display styled multi-line file lists. The Phase 7 research noted this (see `DiagramViewer.tsx` Phase 06-03 note: "Lucide LucideProps does not accept title — wrapped AlertCircle in span for tooltip"). Use CSS-based tooltip instead.

- **Showing ChangeBadge when diagram state is not stale:** Only render the badge when state is `stale` and element counts are > 0. On fresh state, `clearAffectedElements` is already called by the store's `transitionToFresh`, so element count will be 0 naturally.

## Common Pitfalls

### Pitfall 1: SVG Timing — `useEffect` Runs Before DOM Update
**What goes wrong:** `useEffect` fires after React renders, but `dangerouslySetInnerHTML` may still be writing to the DOM. The `querySelector('svg')` returns null or stale SVG.
**Why it happens:** React batches DOM updates; `innerHTML` assignment happens synchronously in the commit phase but effect runs after paint. In practice this usually works, but the SVG might not be fully parsed yet on slower machines.
**How to avoid:** Check that `containerRef.current?.querySelector('svg')` is non-null before applying styles. If null, skip (the next `svgContent` change will re-trigger the effect). Alternatively, use a `MutationObserver` on `containerRef.current` for robust detection, but this adds complexity. The simple null-check is sufficient for this use case.
**Warning signs:** Highlight doesn't appear on first diagram load but appears after switching diagrams.

### Pitfall 2: Element ID Mismatch Between Store and SVG
**What goes wrong:** `AffectedElement.elementId` from `ChangeTrackingService` doesn't match the `elem_` ID in the rendered SVG.
**Why it happens:** `ChangeTrackingService.mapFilesToElements()` uses `sanitizeId(capitalizedName)` — e.g., "Services" → `"Services"`. The SVG element is `<g id="elem_Services">`. The match is `"elem_" + elementId`. This should work correctly, but depends on `sanitizeId` being identical in both the generator and the tracking service.
**How to avoid:** Phase 7 verified that both `C4PlantUMLGenerator.sanitizeId` and the exported `sanitizeId` from `changeTrackingService.ts` use identical logic: `name.replace(/[^a-zA-Z0-9_]/g, '_').replace(/^[0-9]/, '_$&')`. No fix needed, but include a console.warn in development mode if a querySelector misses (to help diagnose real-world mismatches).
**Warning signs:** Amber highlight never appears despite `affectedElements` being populated in the store.

### Pitfall 3: `!important` vs PlantUML Inline Styles
**What goes wrong:** Injected `<style>` does not override PlantUML inline `fill="..."` attributes on SVG shapes.
**Why it happens:** CSS specificity: inline `style` attributes beat CSS class selectors. However, a `<style>` rule with `!important` overrides inline `style=""` but NOT inline attributes like `fill="blue"`. In SVG, `fill="blue"` is a presentation attribute, which has lower specificity than CSS rules (even without `!important`).
**How to avoid:** CSS rules in a `<style>` block override SVG presentation attributes (`fill="..."`, `stroke="..."`) without needing `!important`. The `!important` is a safety measure but not strictly required for SVG attributes.
**Verification:** Test by inspecting rendered SVG shapes — their computed style should show the injected fill color when `data-changed="direct"` is set.
**Warning signs:** Background colors remain unchanged despite `<style>` injection.

### Pitfall 4: ChangeBadge Tooltip Clipped by Overflow Hidden Container
**What goes wrong:** The file-list tooltip renders but is visually cut off by a parent container with `overflow: hidden`.
**Why it happens:** `DiagramPanel` uses `overflow-hidden` on its root div (line 90: `className="relative h-full ... overflow-hidden"`). The tooltip positioned `absolute` relative to the badge container will be clipped.
**How to avoid:** Either: (a) move the tooltip to a portal using `ReactDOM.createPortal` into `document.body`, or (b) position the tooltip with a high enough `top` value to escape the overflow container, or (c) change the tooltip trigger to use `position: fixed` instead of `position: absolute`. The simplest approach for Phase 8: use `position: fixed` on the tooltip div with a `useRef` to compute the badge's `getBoundingClientRect()` on hover.
**Warning signs:** Tooltip renders but is partially or fully invisible.

### Pitfall 5: Missing `changedFiles` in Store
**What goes wrong:** `ChangeBadge` cannot render the file-list tooltip because file paths are not accessible — `diagramStateStore` only stores `affectedElements` (element IDs), not the raw file paths.
**Why it happens:** Phase 7 populated `affectedElements` in the store but not `changedFiles`. The raw file paths are in SQLite (`diagram_change_tracking.changed_files`) and in the `StateChangedPayload.changedFiles` IPC event field.
**How to avoid:** Extend `diagramStateStore` to also store `changedFiles: Map<string, string[]>` keyed by `repoPath:level`. Populate it alongside `setAffectedElements` in the IPC handler in `DiagramViewer.tsx`. This is a small store extension (one new Map, one setter, one getter).
**Warning signs:** Tooltip shows "0 files changed" or no tooltip despite knowing files changed.

### Pitfall 6: Re-render Loop from Store Subscription
**What goes wrong:** Reading `affectedElements` from the store causes the entire `DiagramPanel` or `PlantUMLRenderer` to re-render on every state change, including unrelated state updates.
**Why it happens:** `useDiagramStateStore` without a selector re-renders on any store mutation.
**How to avoid:** Use selective Zustand subscriptions: `useDiagramStateStore(s => s.getAffectedElements(repoPath, level))` and `useDiagramStateStore(s => s.getChangedElementCount(repoPath, level))`. These selectors only re-render when the specific slice changes.
**Warning signs:** Diagram re-renders and blinks on every file change event.

## Open Questions

1. **Should ChangeBadge show at all C4 levels or only the currently viewed level?**
   - What we know: `diagramStateStore.getChangedElementCount(repoPath, level)` is level-specific. Phase 7 tracks changes per `(repoPath, level)` separately.
   - What's unclear: If the user is on the Container level, should the badge show container-level changes, component-level changes, or both?
   - Recommendation: Show only the current level's element count in the badge (consistent with how `DiagramStateBadge` already shows per-level stale state). The user is already at the level where changes occurred.

2. **What happens when SVG is rendered via server (not local Java)?**
   - What we know: `PlantUMLRenderer` supports two paths — local Java (generates SVG locally) and server-based (fetches SVG from URL). Both paths set `svgContent` identically.
   - What's unclear: Does the server-rendered SVG use the same `elem_` ID structure as local Java rendering?
   - Recommendation: Assume yes — the `elem_` prefix is a PlantUML convention, not Java-specific. If server rendering produces different IDs, the highlight silently fails (no element found), which is acceptable degradation. Log a warning in dev mode.
   - Risk: LOW — both render paths produce the same PlantUML SVG standard output.

3. **Should `changedFiles` be stored in `diagramStateStore` or fetched on tooltip open?**
   - What we know: Files are already in `StateChangedPayload.changedFiles` (IPC event) and in SQLite `diagram_change_tracking.changed_files`. Fetching on open adds latency but avoids store complexity.
   - Recommendation: Store in Zustand (Option A from Architecture Patterns) — consistent with Phase 7's decision to store `affectedElements` in the store for cold-launch recovery. The file list is small (typically < 20 files) and already transmitted in the IPC payload.
